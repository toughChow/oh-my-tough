# 概念篇：数据包如何在虚拟网络中流动

命令只是操作网络对象的方式。真正需要掌握的是：一个进程产生数据后，Linux 内核根据哪些状态做出哪些决定。

本章暂时不追求记住命令，而是建立一套能反复使用的心智模型。读完后，你应该能在看到任意简单拓扑时回答三个问题：

1. 数据包现在属于哪个网络空间？
2. 内核会把它交给本机、同一链路上的节点，还是某个网关？
3. 下一跳需要使用哪个 IP、MAC 和出口网卡？

## 1. 虚拟网络到底虚拟了什么

现实网络由网卡、网线、交换机、路由器和防火墙组成。虚拟网络没有改变以太网和 IP 的基本规则，只是把这些设备的行为改成由内核或软件实现。

| 现实对象 | Linux 中的虚拟对象 | 主要职责 |
| --- | --- | --- |
| 主机的独立网络环境 | network namespace | 隔离网卡、地址、路由和端口 |
| 网卡 | network interface | 数据包进入和离开网络栈的接口 |
| 网线 | veth pair | 在两个接口之间传递以太网帧 |
| 二层交换机 | Linux bridge | 根据 MAC 地址转发帧 |
| 路由器 | 开启 IP forwarding 的 Linux 网络栈 | 根据路由表转发 IP 包 |
| 防火墙/NAT 设备 | nftables/iptables | 过滤或改写数据包 |

所以虚拟网络并不是“假的网络”。从数据包的视角看，它仍然经过网卡、二层链路和三层路由；只是这些对象不一定对应一块真实硬件。

## 2. 先分清四个经常混淆的东西

### 2.1 应用数据

应用调用 socket 写入的内容，例如 HTTP 请求或一段数据库查询。应用通常只关心目标 IP 和端口，不直接决定 MAC 地址或出口网卡。

### 2.2 TCP/UDP 段

传输层加入源端口、目标端口等信息。端口帮助操作系统把收到的数据交给正确进程。

### 2.3 IP 数据包

网络层加入源 IP、目标 IP、TTL 等信息。IP 地址用于跨网络寻址，路由器主要根据目标 IP 做决定。

### 2.4 以太网帧

二层加入源 MAC 和目标 MAC。MAC 地址只负责当前这段二层链路上的交付。

封装关系可以简化为：

```text
以太网帧
└── IP 数据包
    └── TCP/UDP 段
        └── 应用数据
```

::: tip 最重要的区别
IP 回答“最终要去哪个主机”，MAC 回答“当前这段链路先交给谁”。跨过路由器时，IP 通常保持不变，而以太网帧会被拆掉并重新封装，所以 MAC 会改变。
:::

## 3. network namespace：复制一套网络视角

Linux 主机默认只有一个网络空间，称为初始 namespace。创建新的 network namespace，相当于让同一个内核维护多套相互隔离的网络视图。

每个 namespace 主要拥有自己的：

- 网络接口列表
- IP 地址
- 路由表
- ARP/邻居表
- 防火墙规则
- 监听端口和 socket

这解释了一个常见现象：两个容器都可以在自己的内部监听 `0.0.0.0:80`，因为它们位于不同的网络空间；但把两个端口同时映射到宿主机的 `80` 端口就会冲突，因为宿主机端口属于同一个网络空间。

namespace 不是虚拟机。它没有独立内核，只是让进程看到和使用内核中某一套隔离的网络资源。

```text
同一个 Linux 内核
├── 初始 namespace：eth0、宿主机路由表、宿主机端口
├── namespace A：eth0、自己的路由表、自己的端口
└── namespace B：eth0、自己的路由表、自己的端口
```

不同 namespace 中都可以有一个叫 `eth0` 的接口，因为接口名只要求在所属 namespace 内唯一。

## 4. network interface：内核中的数据入口和出口

`eth0`、`lo`、veth、bridge、TUN 都属于 network interface。它们类型不同，但在路由系统中都可能成为数据包的入口或出口。

理解接口时，要把以下属性分开：

- **状态**：接口是 `UP` 还是 `DOWN`。
- **链路状态**：另一端是否可用。
- **地址**：接口可以拥有零个、一个或多个 IP。
- **所属空间**：一个接口在同一时间只属于一个 namespace。
- **类型**：物理网卡、veth、bridge、loopback 等。

接口存在不等于链路可用，链路可用也不等于三层配置正确。排错时应依次确认：对象存在、接口启用、链路连通、IP 正确、路由正确。

## 5. veth pair：一根没有方向的虚拟网线

veth 必须成对创建。进入一端的以太网帧会从另一端出现：

```text
veth-a  <====================>  veth-b
```

它不负责交换、路由或 NAT，只负责连接。常见用法是：

- 一端放进容器 namespace，另一端接到宿主机 bridge。
- 两端分别放进两个 namespace，形成点对点链路。
- 一端用于测试程序注入流量，另一端用于抓包观察。

如果删除其中一端，整对 veth 都会消失。这与拔掉并丢弃一根两头相连的虚拟网线相似。

## 6. 主机如何判断目标是否在同一子网

假设主机地址是：

```text
10.10.1.2/24
```

`/24` 表示 IP 地址的前 24 位是网络前缀。主机会分别对自己的 IP 和目标 IP 应用子网掩码，然后比较网络前缀。

```text
自己：10.10.1.2   AND 255.255.255.0 = 10.10.1.0
目标：10.10.1.9   AND 255.255.255.0 = 10.10.1.0  → 同一子网
目标：10.10.2.9   AND 255.255.255.0 = 10.10.2.0  → 不同子网
```

判断结果决定的是“下一跳是谁”：

- **同一子网**：下一跳就是目标主机本身。
- **不同子网**：下一跳是路由表选出的网关。

这一步仍然只处理 IP。决定下一跳之后，主机还需要知道下一跳的 MAC 地址，才能在以太网上发送帧。

## 7. ARP：把下一跳 IPv4 地址解析成 MAC

ARP 解决的是同一二层网络中的 `IPv4 → MAC` 映射。

当主机需要发送数据，但邻居表没有下一跳的 MAC 时，会经历：

1. 广播 ARP Request，询问某个 IPv4 地址属于谁。
2. 拥有该地址的节点返回 ARP Reply，告诉请求方自己的 MAC。
3. 请求方把映射缓存到邻居表，避免每个数据包都广播。

关键是 ARP 查询“下一跳”，不一定查询最终目标：

| 场景 | 最终目标 IP | ARP 查询对象 |
| --- | --- | --- |
| 同一子网 | 对端主机 | 对端主机 IP |
| 不同子网 | 远端主机 | 本地网关 IP |

因此一台内网主机访问公网服务器时，通常不会知道公网服务器的 MAC。它只需要知道本地默认网关的 MAC。

::: info IPv6
IPv6 不使用 ARP，而使用 ICMPv6 Neighbor Discovery 完成相似任务。本阶段先聚焦 IPv4。
:::

## 8. Linux bridge：二层交换机如何做决定

bridge 连接多个二层端口，根据 MAC 地址转发以太网帧。它维护一张 FDB（Forwarding Database），可以理解为“MAC 地址在哪个端口”的表。

bridge 收到一个帧时，主要执行四步：

1. **学习源地址**：记录源 MAC 是从哪个端口进来的。
2. **查找目标地址**：在 FDB 中搜索目标 MAC。
3. **选择出口**：已知目标就只发到对应端口；未知目标就向其他端口泛洪。
4. **避免回送**：不会把帧原样从入端口送回去。

```text
FDB
MAC-A  → port 1
MAC-B  → port 2
MAC-C  → port 3
```

需要泛洪的典型流量包括：

- 广播，例如 ARP Request。
- 尚未学习到目标端口的未知单播。
- 某些组播流量。

bridge 根据 MAC 工作，不需要理解常规 IP 路由。因此，一台只承担二层转发的 bridge 可以完全不配置 IP。给 bridge 配 IP 的意义通常是让宿主机自己也参与这个网络或便于管理，而不是让交换功能生效。

## 9. 路由表：不是一张路线清单，而是一组匹配规则

一条 IPv4 路由通常包含：

- **目标前缀**：这条规则匹配哪些目标 IP。
- **下一跳**：交给哪个网关；直连路由没有下一跳网关。
- **出口接口**：数据从哪里离开。
- **源地址偏好**：本机主动发送时优先选择哪个源 IP。
- **metric**：其他条件相近时用于比较优先级。

例如：

```text
10.10.1.0/24 dev eth0
10.10.0.0/16 via 192.168.1.1 dev eth1
default via 192.168.1.254 dev eth1
```

### 最长前缀匹配

如果多条路由都能匹配目标，内核优先选择前缀更长、范围更具体的那条。这叫最长前缀匹配。

目标 `10.10.1.9` 同时匹配：

```text
0.0.0.0/0
10.0.0.0/8
10.10.0.0/16
10.10.1.0/24
```

最终选择 `/24`，因为它最具体。默认路由 `0.0.0.0/0` 能匹配所有 IPv4 地址，但只在没有更具体路由时兜底。

::: tip 默认网关不是固定概念
“默认网关”只是默认路由所指定的下一跳。主机也可以只配置若干具体静态路由而不配置默认路由。
:::

## 10. 主机和路由器的区别在哪里

主机和路由器都查询路由表。区别不在于设备长什么样，而在于内核如何处理“目标 IP 不是自己”的入站数据包。

- **普通主机**：处理发给自己的包；通常丢弃需要替别人转发的包。
- **路由器**：开启 IP forwarding，允许在不同接口之间转发包。

Linux 开启 `net.ipv4.ip_forward=1` 后，就具备基础 IPv4 路由能力。它不需要额外安装一个名为“路由器”的程序。

路由器转发一个普通 IPv4 包时，会：

1. 去掉收到的二层帧封装。
2. 检查目标 IP，并查询自己的路由表。
3. 把 TTL 减一；减到零时丢弃数据包，通常返回 ICMP Time Exceeded。
4. 确定出口接口和下一跳。
5. 必要时用 ARP 获取下一跳 MAC。
6. 使用出口链路的新 MAC 地址重新封装并发送。

TTL 防止路由配置错误时数据包在环路中无限转发，`traceroute` 也正是利用 TTL 和超时报文观察逐跳路径。

## 11. 两种通信场景的完整对比

### 场景 A：同一子网

```text
host A: 10.10.0.1/24  ── bridge ──  host B: 10.10.0.2/24
```

数据路径：

```text
应用
→ 查路由：目标属于直连网络
→ ARP 查询 10.10.0.2 的 MAC
→ 封装目标 MAC 为 host B 的以太网帧
→ bridge 根据 FDB 转发
→ host B 接收
```

特点：不经过网关，不发生三层转发，bridge 不修改 IP 包。

### 场景 B：不同子网

```text
host A                router                 host B
10.10.1.2/24    10.10.1.1 | 10.10.2.1    10.10.2.2/24
```

数据路径：

```text
应用
→ 查路由：目标不在本地，命中默认路由
→ ARP 查询网关 10.10.1.1 的 MAC
→ 第一段帧交给 router
→ router 拆帧、TTL - 1、再次查路由
→ router ARP 查询 10.10.2.2 的 MAC
→ 用新的二层地址封装第二段帧
→ host B 接收
```

对比每一层：

| 字段/状态 | 同一子网 | 跨路由器 |
| --- | --- | --- |
| 源/目标 IP | 端到端保持 | 通常端到端保持 |
| 源/目标 MAC | 一段链路使用一组 | 每一跳重新封装 |
| TTL | 不经过路由器时不减 | 每次三层转发减一 |
| ARP 对象 | 最终目标 | 当前链路的下一跳 |
| 决策依据 | bridge 查目标 MAC | router 查目标 IP |

## 12. 回程路径为什么同样重要

`ping` 包能到达目标，不代表一定能收到回复。目标必须知道如何把响应送回源地址。

例如 A 能通过路由器访问 B，但 B 没有返回 A 所在子网的路由：

```text
A → router → B       请求到达
A ←   ?     ← B      B 不知道响应交给谁
```

排错时不能只检查去程。需要从目标节点反向执行路由查询，确认回程下一跳正确。复杂网络还可能出现去程和回程不一致的非对称路由，它不一定错误，但会影响状态防火墙和连接跟踪。

## 13. 这些概念如何映射到容器和云网络

### Docker bridge 模式

```text
容器进程
→ 容器 network namespace
→ 容器 eth0
→ veth pair
→ 宿主机 bridge
→ 宿主机路由/NAT
→ 外部网络
```

容器看到的 `eth0` 往往就是一对 veth 的一端；另一端位于宿主机并接入 Docker 创建的 bridge。

### Kubernetes Pod 网络

Pod 通常拥有自己的网络空间。CNI 插件负责创建接口、配置 IP 和路由，并可能使用 bridge、路由或 VXLAN 等不同数据平面。插件实现不同，但内核最终仍需要回答“从哪个接口把包送给哪个下一跳”。

### 云 VPC

VPC 在使用体验上暴露子网、路由表、安全组、NAT 网关等对象。底层实现可能是分布式的，不一定真的存在一台对应的物理路由器，但对使用者来说仍可用相同模型推理：匹配路由、确定下一跳、应用安全策略、完成转发。

## 14. 常见误区

### “能 ping IP，说明网络完全正常”

ping 只验证 ICMP 的部分路径。应用仍可能因为 DNS、端口、防火墙、MTU、TCP 状态或应用监听地址失败。

### “bridge 就是路由器”

bridge 主要按 MAC 做二层转发；路由器按目标 IP 做三层转发。Linux 可以同时承担两种角色，但这是两个不同过程。

### “默认网关知道互联网所有路线”

主机只是假设默认网关更知道怎么走。网关仍然需要继续查自己的路由表，可能再次交给另一个下一跳。

### “同一 IP 网段一定能互通”

IP 配置相同不代表二层链路真的连通。VLAN、bridge 端口状态、防火墙和错误的 namespace 归属都可能阻断通信。

### “namespace 隔离了整个操作系统”

network namespace 只隔离网络相关资源。容器通常还会组合 PID、mount、user 等其他 namespace，再配合 cgroup 限制资源。

## 15. 一套通用的数据包排查顺序

遇到“不通”时，从局部事实向外检查：

1. **进程**：应用是否监听正确地址和端口？
2. **接口**：目标 namespace 中接口是否存在且为 UP？
3. **地址**：IP 和掩码是否正确？
4. **选路**：`ip route get 目标IP` 会选哪个出口和下一跳？
5. **邻居**：下一跳的 ARP/邻居状态是否正常？
6. **链路**：veth、bridge 端口或 VLAN 是否连接正确？
7. **转发**：中间节点是否开启 IP forwarding？
8. **策略**：防火墙、NAT、策略路由是否改变了结果？
9. **回程**：目标返回源地址时会选择哪条路？
10. **抓包**：数据在哪个接口消失，进入前后字段发生了什么？

抓包应该用于验证推理，而不是一开始就盯着大量报文猜测。

## 16. 自测题

1. network namespace 与虚拟机最大的区别是什么？
2. veth、bridge、router 分别解决连接、交换还是选路问题？
3. `10.10.1.2/24` 访问 `10.10.1.8` 时 ARP 查询谁？访问 `10.10.2.8` 时呢？
4. 为什么 bridge 不配置 IP 仍然可以转发帧？
5. 默认路由、`10.0.0.0/8` 和 `10.10.1.0/24` 同时匹配时选哪一条？
6. 数据包经过路由器时，IP、MAC 和 TTL 分别如何变化？
7. 去程正确、回程没有路由时，从客户端看会出现什么现象？

::: details 参考答案
1. namespace 共享宿主机内核，只隔离一套网络资源视图；虚拟机通常拥有独立内核。
2. veth 负责连接，bridge 负责二层交换，router 负责三层选路与转发。
3. 同子网查询 `10.10.1.8`；跨子网查询路由选出的本地网关，而不是远端 `10.10.2.8`。
4. bridge 按 MAC 和 FDB 工作，普通二层转发不依赖自身 IP。
5. 选择最长、最具体的 `/24`。
6. 没有 NAT 时源/目标 IP 通常不变；二层 MAC 每跳重写；TTL 每经过一次三层转发减一。
7. 请求可能到达目标，但客户端收不到响应，表现为超时。
:::
